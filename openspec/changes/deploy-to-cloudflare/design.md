## Context

- Next.js 16.4.6 App Router app with server actions (`src/app/admin/actions.ts`), Prisma 6 + `@prisma/client`, SQLite file at `prisma/dev.db`, Tailwind 4 via `@tailwindcss/turbopack` in `next.config.ts`.
- Single `PrismaClient` instance in `src/lib/db.ts` used by server code.
- Cloudflare Workers has no filesystem and no long-lived Node process; SQLite files and `next start` are not viable there.
- User chose **vinext** (Cloudflare's recommended Next.js-on-Workers path) and **Cloudflare D1** for the database.

## Goals / Non-Goals

**Goals:**
- Deploy the app to Cloudflare Workers with all existing features (pages, server actions, admin mutations).
- Move persistence to D1 accessed through Prisma's D1 driver adapter.
- Keep `next dev` local development working without requiring Cloudflare credentials.
- Repeatable migrations and seeding for the D1 database.

**Non-Goals:**
- Changing application features or UI.
- Multi-environment CI/CD pipelines beyond manual `wrangler` deploys.
- Supporting `next build`/`next start` as a production target (local-only).

## Decisions

### 1. vinext for the Workers runtime
Use `vinext` + `@vinext/cloudflare` per Cloudflare's current framework guide. `vinext init` is non-destructive — existing `next dev` keeps working, and vinext adds its own dev/build scripts.
- *Alternative considered*: OpenNext adapter (`@opennextjs/cloudflare`) — more battle-tested, but Cloudflare now recommends vinext and it is in active development. Chosen per user preference; `vinext check` will flag incompatibilities before we commit.

### 2. D1 via `@prisma/adapter-d1` driver adapter
Keep Prisma as the ORM but instantiate `PrismaClient` with the D1 driver adapter bound from the Workers `env` (accessed via `cloudflare:workers`). The Prisma schema keeps `provider = "sqlite"` (D1 is SQLite-compatible); the file `url` becomes irrelevant in the Workers path.
- `src/lib/db.ts` will branch: on Workers, create the adapter from the D1 binding; in plain Node (`next dev`), fall back to the existing SQLite client so local dev needs no Cloudflare account.
- *Alternative considered*: raw D1 client / Drizzle — rejected to keep the existing Prisma models and queries unchanged.

### 3. Migrations via generated SQL + Wrangler, not `prisma migrate`
`prisma migrate` does not support D1. Generate SQL with `prisma migrate diff` (or `migrate dev` against a shadow/local SQLite then export) and apply it with `wrangler d1 migrations apply` / `wrangler d1 execute`. Keep generated SQL under `prisma/migrations-d1/` or Wrangler's `migrations_dir` so deploys are repeatable.
- Seed script (`prisma/seed.mjs`) will be runnable against D1 (via `wrangler d1 execute --file` or a small script using the adapter).

### 4. Config files
- `wrangler.jsonc` (or `.toml`): Worker name, `main` entry generated by vinext, `assets` for static files, `d1_databases` binding (e.g. `DB`).
- `vite.config.ts` for vinext; package.json scripts: `dev:vinext`, `build:vinext`, `deploy` (wrangler deploy of the vinext output).
- `cloudflare-env.d.ts` via `wrangler types` for typed bindings.

### 5. Env vars
`DATABASE_URL` remains for the SQLite fallback path; production D1 needs no connection string — only the binding. Any secrets (e.g., admin password hash) move to `wrangler secret` / `.dev.vars`.

## Risks / Trade-offs

- [vinext is beta; some Next.js features may be unsupported] → Run `npx vinext check` first; if server actions or `next/*` imports are flagged, evaluate OpenNext fallback before proceeding.
- [Prisma + D1 adapter cold-start/perf limits] → App is low-traffic; acceptable. D1 has per-query limits; keep queries simple (current usage is).
- [SQLite → D1 data migration] → Export `prisma/dev.db` (e.g., `sqlite3 .dump` or D1 import of a SQL dump) into the production D1 database during setup.
- [Two DB paths (SQLite local, D1 prod) can drift] → Both use the same `schema.prisma`; migration SQL is generated from it, keeping parity.
- [Turbopack CSS rule in `next.config.ts`] → vinext uses Vite; Tailwind 4 works via `@tailwindcss/vite` or the existing PostCSS setup — verify during `vinext init` and adjust config if the turbopack rule is ignored.

## Migration Plan

1. Run `npx vinext check`; resolve or document issues.
2. `npx vinext init` → Cloudflare Workers target; add `wrangler` config.
3. Install `@prisma/adapter-d1`, `wrangler`; create D1 database; bind it in wrangler config.
4. Update `src/lib/db.ts` for the adapter + fallback; generate and apply D1 migrations; port seed script.
5. Import existing `dev.db` data into D1.
6. `build:vinext` + `deploy`; smoke-test pages and admin server actions on the workers.dev URL.
7. Rollback: the deployed Worker can be deleted/`wrangler rollback`; local `next dev` path is untouched.

## Open Questions

- Exact vinext-generated config file names (`wrangler.jsonc` vs `wrangler.toml`, Vite config shape) — determined by `vinext init` output at implementation time.
- Whether vinext handles the `experimental.serverActions.allowedOrigins` / `allowedDevOrigins` settings — likely ignorable in production; verify during implementation.
